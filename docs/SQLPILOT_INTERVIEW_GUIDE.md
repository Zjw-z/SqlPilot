# SQLPilot 面试讲解手册

> 使用原则：先讲业务问题和设计取舍，再讲技术实现；不把 Spider 指标说成医保生产准确率，不把规划中的 Oracle/MySQL、Neo4j、LangGraph 说成已经完成。

## 1. 三分钟项目介绍

SQLPilot 是一个面向医保结算分析的可信 Text-to-SQL Agent。它解决的不是单纯让大模型生成一条能运行的 SQL，而是让业务人员能够看懂、确认并追溯一次查询。

用户通过多轮对话描述指标、维度、时间范围、过滤条件和同比环比需求。系统首先调用百炼 Qwen，把自然语言整理成强类型 QueryPlan。需求不完整时不会猜测，而是针对指标口径、时间、统计粒度或相似字段进行追问。计划完整后展示给用户确认，确认版本和最终执行版本通过哈希绑定，防止后续内容漂移。

数据源接入后，后台会扫描 PostgreSQL 的表、字段、注释、外键和低基数字典值。系统以字段为主要粒度，将表信息、字段信息、业务别名和字典值组合成语义文档，使用 DashScope Embedding 生成向量并存入 pgvector；检索时叠加 pg_trgm 词法相似度和外键关系扩展，完成 Schema Linking。指标、维度、码值和 JOIN 还可以进入人工认证的语义层，认证口径优先于模型判断。

标准的单事实表聚合、月度统计、同比环比和 Top-N 查询由确定性编译器生成 SQL；复杂长尾需求才使用模型生成候选 SQL。无论哪条路径，都必须通过 SQLGlot AST 只读校验、Schema 白名单、QueryPlan 一致性校验、EXPLAIN 成本门禁、只读事务、超时和最大行数限制。执行后系统自动生成中文列名、图表配置、数据摘要、关键发现、风险提示和可信等级。

我还建设了反馈审核和查询路径学习闭环：只有用户确认结果正确且审核通过的结构化计划才能被复用；路径记录字段依赖和 Schema 指纹，结构变化后会自动失效。项目使用本地医保测试库验证业务流程，同时使用 Spider 1.0 dev 全量 1,034 条进行跨领域评测，执行结果一致率为 88.10%。

## 2. 一句话架构

模型负责把自然语言理解成结构化意图，程序负责口径约束、Schema 绑定、SQL 编译、安全校验和执行，人工负责高风险歧义与业务知识认证。

## 3. 一次查询的完整实现过程

### 3.1 创建会话并发送需求

前端调用会话 API，`ConversationService.send_message()` 保存用户消息，读取上一版本计划、数据源、用户记忆和已认证查询路径。

关键代码：

- `app/api_v1/routes.py`：HTTP API。
- `app/conversation/service.py`：主流程状态机。
- `app/conversation/repository.py`：消息、计划版本和执行记录持久化。

### 3.2 检索相关 Schema

`DataSourceService.search()` 从当前激活的 Schema 知识版本中检索表、字段和关系。`PgVectorKnowledgeStore.search()` 同时计算向量相似度与词法相似度，再返回业务名称、技术字段、来源和分数。

字段文档大致为：

```text
Schema nhsa；表名 setl_d；表注释 医保结算明细；
字段名 fund_pay_sumamt；字段类型 numeric；
字段注释与业务别名 基金支付总额；
低基数字典值 ...
```

为什么按字段构建：用户通常问的是“基金支付总额”“结算人次”这类字段语义，整表向量会被大量无关字段稀释；字段级召回后仍保留表上下文，可以继续做表选择和 JOIN 规划。

关键代码：

- `app/data_sources.py`：扫描 Schema、生成知识文档、后台同步。
- `app/knowledge_store.py`：Embedding、pgvector 版本切换和混合检索。
- `app/text_to_sql/schema.py`：把召回结果组装成执行阶段的 `SchemaContext`。

### 3.3 生成或修改 QueryPlan

`BailianQueryPlanner`要求模型输出符合 Pydantic Schema 的 JSON，而不是 SQL。QueryPlan主要包含：

- 指标、维度、过滤条件；
- 时间范围及对比区间；
- 排序、Top-N和统计范围；
- Schema证据和语义绑定；
- 澄清问题、默认业务规则和数据源ID；
- 结构化SQL语义，如输出字段、聚合、分组、HAVING和集合逻辑。

多轮修改时会把上一版本计划和用户新增内容一起交给模型，同时由程序保护用户未要求修改的字段，避免一句“再加同比”把原有指标和维度清空。

关键代码：

- `app/planning/models.py`：QueryPlan强类型模型、依赖检查和稳定哈希。
- `app/planning/bailian.py`：百炼调用、JSON解析、规范化和多轮需求保护。

### 3.4 澄清与用户确认

当指标没有确定字段、相似字段分数过近、时间口径缺失或统计范围确实会改变结果时，计划进入 `clarifying` 状态并返回结构化选项。澄清完成后生成新版本。用户点击确认时，需要同时提交版本号和计划哈希；服务端重新核对后才将计划标记为已确认。

关键点：追问由模型提出，但程序会清理重复、无意义或已经回答的问题；不采用“看到某个关键词就强制追问”的硬编码业务规则。

### 3.5 应用认证语义层

`SemanticLayerService.apply_certified()`读取当前数据源已认证的指标、维度、码值和 JOIN 定义，并替换或补强模型产生的绑定。语义定义具有 draft、certified、disabled 状态，未经认证的草稿不能静默影响生产查询。

关键代码：`app/semantic_layer.py`。

### 3.6 双通道生成 SQL

第一通道是 `DeterministicQueryCompiler`。当需求属于已支持的标准分析子集，并且指标、维度、过滤和时间字段都绑定在同一事实表时，程序直接从 QueryPlan 编译 SQL。这条路径可预测、容易测试，也能保证确认计划和 SQL 一致。

第二通道是 `BailianSqlGenerator`。多表、复杂集合逻辑或编译器尚未覆盖的长尾需求由模型生成多个候选 SQL。模型只能看到召回后的候选 Schema，不能访问整个数据库；候选必须通过与确定性 SQL 相同的校验门禁。

关键代码：

- `app/text_to_sql/compiler.py`：确定性编译器。
- `app/text_to_sql/generator.py`：模型候选生成。
- `app/text_to_sql/engine.py`：双通道编排、校验、修正和执行。

### 3.7 SQL 校验与有限重试

`PostgresSqlValidator`使用 SQLGlot 将 SQL 解析为 AST，主要检查：

1. 只能有一条 SELECT/WITH，禁止 INSERT、UPDATE、DELETE和DDL。
2. 引用的表和字段必须来自本次动态 Schema 白名单。
3. 输出列、聚合、GROUP BY、HAVING、过滤值、排序和集合逻辑必须与 QueryPlan 一致。
4. 时间结束边界使用半开区间，避免 `23:59:59`遗漏小数秒数据。
5. 同比必须覆盖同期区间，关联方向和增长率公式必须正确。

模型 SQL 校验失败最多修正3轮；数据库试执行错误最多修正2轮。超过次数后停止自动尝试，保留已确认计划，向用户返回可操作建议，而不是无限循环或降低安全规则。

关键代码：`app/text_to_sql/validator.py`、`app/text_to_sql/engine.py`。

### 3.8 安全执行

执行前先用 `EXPLAIN (FORMAT JSON)`检查预计扫描行数和成本。正式执行在 PostgreSQL只读事务内进行，并设置 statement timeout 和最大返回行数。查询会被外层 SELECT 包装并增加行数上限，前端只拿到受控结果。

注意：数据库账号本身仍应配置为只读账号；应用层只读校验属于第二道防线，不能替代数据库最小权限。

### 3.9 结果展示与可信证据

系统根据结果字段推断中文标题、数值类型和单位。时间+指标优先折线图，分类+指标优先柱状图；多个不同量纲的指标会拆分图表，避免金额和人次共用一个纵轴造成误读。模型基于实际返回数据生成摘要、关键发现和风险提示，不能补充结果中不存在的事实。

可信结果同时返回：数据源、使用表、Schema证据、SQL生成策略、校验结果、EXPLAIN成本、修正次数、结果告警和A-D可信等级。

关键代码：`app/text_to_sql/presentation.py`、`app/text_to_sql/insights.py`、`app/text_to_sql/engine.py`。

## 4. 简历六条职责应该怎么讲

### 4.1 需求理解与多轮交互

不要只说“调用了大模型”。应说明：通过JSON Schema约束输出，以QueryPlan作为模型与执行层的协议；通过版本号、稳定哈希和未提及需求保护解决多轮漂移。

### 4.2 动态 Schema RAG

重点讲数据源接入后自动建环境：扫描元数据、生成字段/表/关系文档、批量Embedding、写入新版本、原子激活、保存Schema指纹。再说明字段向量、词法召回、字典值和关系扩展各自解决什么问题。

### 4.3 业务语义治理

RAG解决“可能是哪一个字段”，语义层解决“企业正式规定必须是哪一个字段、如何聚合、如何去重”。认证知识优先于模型，但必须可审核、可停用、可随Schema变化失效。

### 4.4 SQL生成与自修正

确定性编译器覆盖高频标准查询，模型覆盖长尾；不是完全不用模型，也不是完全相信模型。修正只允许修复SQL，不能偷偷改变QueryPlan。

#### 怎么判断确定性编译器能不能覆盖

系统不会先让大模型试着写SQL，而是由`CapabilityRouter`读取已经确认的QueryPlan和Schema绑定结果，按以下顺序判断：

1. **先判断是否允许继续**：计划仍有待澄清项就返回用户确认；涉及越权或系统不支持的查询意图就拒绝；绑定字段已经不存在时要求重新同步Schema。
2. **再检查语义和Schema是否完备**：每个指标、维度、过滤条件和时间字段都必须绑定到真实字段；聚合方式必须明确且受支持；多表查询必须存在经过认证、方向和基数明确的连接路径。缺少这些前置条件时不进入SQL生成，而是继续澄清。
3. **最后计算查询需要的能力集合**：例如聚合、过滤、分组、排序、Top-N、同比环比、明细查询、多表JOIN、HAVING、分区排名、复杂表达式和非AND逻辑。Router把这组能力与编译器的能力矩阵比对，而不是按“单表简单、复杂就模型”这种模糊规则判断。

当前编译器完整支持聚合、过滤、分组、排序、Top-N以及标准同比环比等组合时，路由为`deterministic`，由程序把QueryPlan逐项翻译成SQL AST。业务含义和字段已经确定，但包含编译器尚未实现的合法表达模式，例如复杂多表查询、HAVING、窗口排名或复杂布尔条件时，路由为`model_fallback`，让大模型在受限Schema和已确认QueryPlan内生成候选SQL。模型只能改变SQL表达，不能改指标、时间范围和过滤口径，生成结果仍要经过同一套安全、Schema和计划一致性校验。

Router最终只产生五种明确结果：

- `deterministic`：编译器能力完整覆盖，确定性生成；
- `model_fallback`：语义已确定，但SQL表达超出编译器覆盖范围；
- `clarify`：业务口径、字段绑定或JOIN前置条件不完整；
- `reject`：越权、敏感或系统不支持的查询；
- `resync_schema`：计划引用的Schema对象已失效，需要重新同步元数据。

面试时可以这样回答：“我没有按SQL看起来复杂不复杂来拍脑袋路由，而是先把QueryPlan转换成能力集合，再与确定性编译器的能力矩阵做匹配。覆盖完整就由程序生成；语义确定但表达能力暂未覆盖才交给模型；语义不清、Schema失效和权限问题分别进入澄清、重同步和拒绝。这样可以保证模型兜底不会绕过业务口径和安全边界。”

**例子**：查询“按医院统计今年医疗总费用并取前10名”，需要聚合、按医院分组、时间过滤、降序和Top-N，能力矩阵全部支持，所以走确定性编译器；查询“各地区内费用排名前三的医院”，需要分区窗口排名，如果编译器暂未覆盖该操作符，但地区、医院、费用字段和口径均已确认，则走大模型兜底；如果“医疗费用”同时命中总费用和基金支付额且无法区分，则先澄清，不允许任何生成路径猜测字段。

### 4.5 安全与一致性校验

强调是多层防御：AST只读、Schema白名单、计划一致性、执行成本、只读事务、超时、行数限制和只读数据库账号。

### 4.6 结果分析与工程化

查询结果不是终点。系统还要帮助业务人员理解结果，并把每一步证据暴露出来；后台评测、历史记录和反馈审核使系统能够持续迭代。

## 5. 高频追问与回答

### 为什么不用大模型直接写SQL？

直接生成SQL的问题是需求、业务口径和执行语句混在一起，用户无法确认，错误也很难定位。QueryPlan把问题分成需求理解、字段绑定和执行三层；模型负责语义泛化，程序负责确定性与安全。

### 为什么不用纯规则解析需求？

自然语言表达开放，规则很难覆盖同义词、省略和多轮补充。模型更适合理解语言，但输出必须进入强类型协议，并由程序检查依赖和业务约束。

### 为什么向量检索还需要pg_trgm？

向量适合同义表达，词法检索适合字段缩写、代码和精确术语。两者融合可以兼顾语义泛化和精确匹配；字典值匹配还能把“住院”等值定位到正确码值字段。

### 两个字段含义接近怎么办？

都保留为候选，结合认证语义层、表上下文、字段值和关系证据重排；仍然接近时显式追问用户，不把Top-1当成事实。

### 为什么暂时不用Neo4j？

当前关联主要来自外键和人工认证JOIN，关系规模不大，用PostgreSQL关系表和内存图遍历已经足够。只有出现大规模多跳血缘、复杂图算法和独立图查询需求时，Neo4j的收益才超过运维成本。

### 为什么限制修正轮次？

无限修正会增加成本和延迟，也可能让模型逐渐偏离已确认需求。固定上限可以让失败可预测；超限后应保留计划并让用户补充口径或管理员检查Schema。

### 88.10%是什么准确率？

它是Spider 1.0 dev 1,034条问题的Execution Accuracy：分别执行预测SQL和标准SQL，对规范化结果集进行比较，911条一致。它证明跨领域Text-to-SQL链路能力，不代表医保生产业务准确率。医保上线需要业务专家维护Golden Set并与权威报表对账。

### Schema召回率是不是100%？

评测报告曾统计“标准SQL目标表是否出现在Top-12候选表中”为100%，但Spider单库表较少且Top-12范围较宽，不能表述成整体Schema Linking 100%，因此简历中不使用这个数字。

### 如何支持Oracle和MySQL？

当前正式执行器是PostgreSQL。后续应抽象数据源适配器，分别实现连接、系统目录扫描、注释和外键读取、执行计划、只读会话和分页；编译器按方言渲染日期、类型转换、字符串匹配、空值和分页语法，SQLGlot校验也按数据源选择方言。不能只更换连接字符串。

## 6. 项目不足应该怎样回答

1. 当前业务Golden Set还不够完整，88.10%来自Spider而非医保生产数据。
2. 正式执行器当前只覆盖PostgreSQL，Oracle和MySQL仍需数据源与方言适配。
3. 确定性编译器主要覆盖单事实表标准分析，复杂多表仍依赖模型候选。
4. 语义层需要业务人员持续认证指标、维度和JOIN口径。
5. 当前不做身份认证和多租户隔离，这是原型阶段明确排除的范围。

回答不足时应紧接解决路径，不要把不足包装成已经完成。

## 7. 十分钟演示脚本

1. 打开数据源管理，展示默认医保数据源和Schema同步状态。
2. 在Schema管理中展示表注释、字段注释、别名和字典值。
3. 输入：“统计2026年各医疗机构住院医保基金支付总额、医疗总费用和结算人次。”
4. 展示结构化QueryPlan中的指标、维度、时间和过滤条件。
5. 补充：“按月展示，并与去年同期比较增长率。”
6. 说明新计划保留了原指标，同时新增月份和同比。
7. 确认并执行，展示SQL、中文表格、图表、数据解读和可信证据。
8. 对结果提交“正确”反馈，再到审核页面说明查询路径如何沉淀。
9. 展示历史查询与评测中心。

演示前必须检查模型配置、数据库、Embedding服务和Schema知识版本，不在面试现场临时同步全库。

## 8. 七天熟悉计划

- 第1天：能脱稿讲三分钟介绍和完整流程。
- 第2天：阅读 `planning/models.py`、`planning/bailian.py`，手写QueryPlan示例。
- 第3天：阅读 `data_sources.py`、`knowledge_store.py`，讲清字段向量和混合检索。
- 第4天：阅读 `compiler.py`、`validator.py`，选一条同比SQL逐段解释。
- 第5天：阅读 `engine.py`，画出生成、校验、修正、执行状态图。
- 第6天：完整演示一次，并回答本手册中的高频追问。
- 第7天：模拟面试，重点练习准确率口径、架构取舍和项目不足。

## 9. 最后必须记住的边界

- 真实向量库是PostgreSQL + pgvector，不是Milvus。
- 当前没有使用LangGraph，主流程由服务层状态机组织。
- 当前没有使用Neo4j，表关系来自外键、认证JOIN和依赖图。
- 当前正式支持PostgreSQL；Oracle/MySQL是下一阶段扩展。
- Spider EX 88.10%不是医保生产准确率。
- Top-12目标表覆盖100%不等于Schema Linking准确率100%。
