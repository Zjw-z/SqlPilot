# SQLPilot 产品级技术设计文档

文档版本：V1.0  
文档状态：设计基线  
适用范围：当前 PostgreSQL 原型及生产化演进  

## 1. 文档目标

本文说明 SQLPilot 从产品需求、Agent 架构、数据源接入、Schema RAG、QueryPlan、多轮对话、语义治理、SQL 生成、安全执行、结果解读、记忆学习、数据安全、测试评估到部署运维的完整设计。

如需按照程序真实顺序学习，请配合阅读 `docs/SQLPILOT_EXECUTION_WALKTHROUGH.md`。该文档先讲数据源接入、Schema扫描、向量构建和语义认证等离线准备，再从HTTP入口逐步说明在线查询的函数、输入输出、分支和失败处理。

状态标记：

- **已实现**：当前代码中存在并可以验证。
- **待生产化**：已有原型能力，但正式上线前需要增强。
- **规划**：尚未进入正式运行链路。

## 2. 产品定位

SQLPilot 是面向医保数据分析的可信自然语言查询 Agent。用户通过中文描述统计需求，系统将需求转成可确认的结构化计划，在动态数据库结构和认证业务口径约束下生成只读 SQL，最后输出表格、图表、文字解读和证据链。

系统重点解决：

1. 业务人员不会写 SQL。
2. 自然语言需求存在省略、歧义和多轮变化。
3. 数据库字段名缺少业务语义。
4. 相似指标可能对应不同字段和口径。
5. 模型 SQL 可能虚构字段、遗漏过滤或产生危险语句。
6. SQL 能执行不等于业务结果正确。
7. 查询结果需要可解释、可追溯、可审核。

## 3. 设计原则

1. **模型理解、程序约束**：模型处理开放语言，程序控制协议、安全和执行。
2. **先计划、后 SQL**：用户先确认 QueryPlan，不直接确认难以阅读的 SQL。
3. **认证口径优先**：正式业务定义高于模型推测和普通检索结果。
4. **确定性编译优先**：高频标准查询使用编译器，复杂长尾才由模型兜底。
5. **默认拒绝高风险请求**：无法证明安全时不执行。
6. **结果可追溯**：记录使用的 Schema、语义绑定、SQL 路径、校验和成本。
7. **反馈不直接污染知识**：用户反馈必须审核后才能成为可复用路径。

## 6A. 身份认证、用户管理与会话隔离

### 6A.1 核心对象

`users`表保存用户ID、租户ID、登录名、显示名称、密码哈希、角色、状态、令牌版本和最近登录时间。密码只保存`PBKDF2-HMAC-SHA256`派生结果、随机盐和迭代次数，不保存或回传明文。

当前角色分为`admin`和`analyst`：管理员可以管理用户；分析人员进行自然语言查询，只能读取自己的查询会话。账号状态分为`active`和`disabled`。

当前属于基础RBAC。治理接口权限矩阵、患者级授权、部门数据范围及行列级权限尚未完成，不能因为用户已经登录就允许患者级敏感查询。

### 6A.2 登录和令牌

```text
提交用户名和密码
→ 查询同租户用户
→ 校验PBKDF2密码哈希
→ 检查账号状态
→ 更新最近登录时间
→ 签发HMAC令牌
→ 写入HttpOnly、SameSite=Lax Cookie
```

令牌包含`user_id`、`tenant_id`、`token_version`、签发时间和过期时间。后续请求由服务端验签并重新读取用户状态，不再接受前端自报的`X-User-Id`。生产环境Cookie还会启用`Secure`，并要求HTTPS。

密码重置、账号停用和主动修改密码会增加`token_version`。数据库版本与令牌版本不一致时，旧登录态立即失效；退出登录则删除浏览器Cookie。

### 6A.3 用户与会话归属

```text
tenant_id
└─ user_id
   └─ conversation_id
      ├─ messages
      ├─ QueryPlan V1 → V2 → V3
      └─ executions/result snapshots
```

创建会话时，租户和用户来自已验证令牌。列出或读取会话时，仓储层同时匹配会话ID、租户ID和用户ID。归属不匹配统一返回404，避免攻击者利用响应差异探测其他用户的会话。

`conversation_id`负责隔离不同分析任务；`plan_version`只负责同一会话的多轮版本和并发覆盖保护，两者不能相互替代。

### 6A.4 用户管理与旧数据迁移

管理员可以创建用户、分配角色、启停账号以及重置密码。新用户和被重置密码的用户标记为`must_change_password`，首次登录后提示修改，修改完成后要求重新登录。

系统第一次启用认证时创建初始管理员，并把原型阶段属于`local-user`的会话、偏好和反馈一次性迁移给初始管理员，防止已有历史记录不可见。

### 6A.5 配置与生产要求

```text
AUTH_REQUIRED=true
SQLPILOT_SECRET_KEY=<独立高强度随机密钥>
BOOTSTRAP_ADMIN_USERNAME=<初始管理员用户名>
BOOTSTRAP_ADMIN_PASSWORD=<一次性强密码>
```

初始管理员只在用户表为空时创建，部署后必须立即修改初始密码。`SQLPILOT_SECRET_KEY`不应与百炼API Key共用；密钥轮换会使已有令牌失效。正式上线还应增加登录频率限制、连续失败锁定、CSRF令牌、认证审计落库以及企业统一身份源对接。

## 7. 端到端时序

### 7.1 需求分析阶段

1. 用户选择数据源并发送自然语言问题。
2. 会话服务保存消息，读取上一版计划。
3. 检索当前数据源相关 Schema、业务记忆和认证查询路径。
4. 规划器将上下文发送给百炼，要求输出严格 JSON。
5. Pydantic 验证类型、枚举、依赖和协议外字段。
6. 多轮保护恢复用户本轮没有要求删除的旧需求。
7. Schema Linking 将业务概念关联到表、字段和值。
8. 认证语义层覆盖正式指标和码值口径。
9. 信息不足则生成结构化追问；完整则保存计划新版本。

### 7.2 确认和执行阶段

1. 前端展示指标、维度、时间、条件、对比和排序。
2. 用户提交计划版本号和稳定哈希进行确认。
3. 服务端验证当前版本没有发生变化。
4. 安全策略检查查询粒度及敏感字段。
5. 编译器判断 QueryPlan 是否属于确定性能力范围。
6. 标准单事实表分析由编译器生成 SQL。
7. 复杂查询由模型生成多个候选 SQL。
8. SQLGlot 校验所有候选，必要时有限修正。
9. EXPLAIN 检查估算行数和成本。
10. 在只读事务中执行，限制超时和返回行数。
11. 保存 SQL、结果、校验证据和执行事件。
12. 生成中文结果、图表和文字解读。

## 8. QueryPlan：Agent 的中间协议

QueryPlan 是自然语言与 SQL 之间的中间表示，主要字段包括：

- 意图：汇总分析、明细查询或不支持。
- 统计指标：业务指标列表。
- 分析维度：医院、月份、疾病类别等。
- 过滤条件：字段、操作符、数据库真实值和展示值。
- 时间范围：开始、结束、同期区间和时间口径。
- 对比方式：无、同比或环比。
- 排序范围：指标、方向和 Top-N。
- 语义绑定：业务概念到真实 Schema 字段。
- Schema 证据：召回对象、分数和歧义状态。
- SQL 语义：输出列、聚合、分组、HAVING、去重及集合逻辑。
- 澄清问题：问题、原因和候选选项。
- 来源信息：模型、Prompt 和目录版本。

QueryPlan 的价值：

1. 用户可以在执行前理解系统意图。
2. SQL 修正不能静默改变业务需求。
3. 可以分别评测需求理解、Schema 绑定和 SQL 生成。
4. 确定性编译器和模型 SQL 可以共享同一输入协议。
5. 计划可以版本化、审核和复用。

## 9. 多轮对话设计

每次补充都会产生新的不可变计划版本。修改计划时，模型必须返回本轮变更字段；程序恢复未被明确修改的上一轮指标、维度、过滤和时间条件。

需要追问的典型情况：

- “费用”没有明确是医疗总费用还是基金支付金额。
- “今年”没有明确使用结算、入院还是出院时间。
- 相似字段召回得分接近且没有认证定义。
- “增长较高”没有明确逐机构比较还是总体比较。
- 过滤意图存在但没有找到数据库真实码值。

不应追问可以从当前问题、上一轮回答和认证口径中唯一确定的内容。

## 10. 动态 Schema RAG

### 10.1 知识构建

数据源同步任务读取：

- Schema、表、字段、类型和可空属性；
- 表注释和字段注释；
- 主外键关系；
- 人工维护的中文名称、描述和别名；
- 适合做业务维度的低基数字典值。

知识文档分为表文档、字段文档和关系文档。字段文档为主要检索粒度：

```text
Schema + 表名 + 表注释 + 字段名 + 字段类型
+ 字段注释 + 业务别名 + 低基数字典值
```

### 10.2 Embedding 与检索

- 模型：DashScope `text-embedding-v4`。
- 默认维度：1,024。
- 向量存储：PostgreSQL pgvector。
- 词法检索：pg_trgm。
- 当前综合得分：`0.7 × 向量分数 + 0.3 × 词法分数`。

向量检索解决同义表达，词法检索解决字段名、缩写和代码精确匹配。字典值用于 Value Linking，例如将“住院”关联到医疗类别字段及正式代码。

### 10.3 知识版本

原始元数据和人工元数据规范化后计算 SHA-256 Schema 指纹。同步过程先写新版本，全部成功后原子激活，防止检索到半成品。Schema 变化会使依赖旧字段的认证查询路径进入失效状态。

### 10.4 敏感信息控制

禁止将姓名、证件号、电话、地址、病历文本等样例值写入向量库。低基数采样必须经过字段类型、名称、注释和敏感标签检查。

## 11. 认证语义层

RAG 回答“可能使用哪个字段”，语义层回答“企业正式规定必须使用哪个字段和口径”。

语义对象包括：

- `metric`：指标字段、聚合方式、单位、去重键和过滤规则。
- `dimension`：维度字段、展示值和时间粒度。
- `value_set`：业务标签到数据库码值映射。
- `join`：连接字段、连接类型、基数和重复聚合策略。
- `business_rule`：有效结算、撤销、退费等规则。
- `golden_query`：经权威确认的典型问题和预期路径。

生命周期：草稿、已认证、停用。只有已认证定义可以自动影响正式计划。

## 12. SQL 生成双通道

### 12.1 确定性编译

当前支持单事实表上的：

- SUM、COUNT、COUNT DISTINCT、AVG、MIN、MAX；
- 多指标和多维度分组；
- 时间范围、业务过滤和默认规则；
- 月份维度；
- 同比、环比；
- 排序和 Top-N。

编译过程：

```text
QueryPlan
→ 检查语义绑定完整性
→ 确认字段来自同一事实表
→ 编译 SELECT 指标和维度
→ 编译 WHERE 时间及过滤
→ 编译 GROUP BY/HAVING
→ 编译同比环比 CTE
→ 编译 ORDER BY/LIMIT
```

### 12.2 模型受控兜底

多表、复杂子查询、集合运算等长尾需求进入模型通道。模型只获得当前 QueryPlan、召回 Schema 和认证关系，不获得数据库连接权限。

每轮可产生多个候选 SQL。所有候选经过同一校验器，选择风险最少的合法候选；全部失败时将去敏后的错误原因反馈给模型，最多修正 3 轮。

### 12.3 分工原则

- 能力范围内：必须走确定性编译。
- 编译器不支持：可以走模型兜底。
- 业务需求不明确：必须追问，不能让模型兜底猜测。
- 确定性 SQL 出错：暴露编译器或环境问题，不用模型掩盖。

## 13. SQL 校验与执行安全

### 13.1 AST 校验

SQLGlot 将 SQL 解析为 AST，然后检查：

- 仅允许一条 SELECT/WITH；
- 禁止 DDL 和 DML；
- 物理表和字段必须属于当前 SchemaContext；
- 字段必须属于正确的表或别名；
- 禁止未授权的敏感表和字段；
- 输出、聚合、过滤、分组、HAVING 和排序与 QueryPlan 一致；
- 时间范围和同比公式完整；
- 未要求的逻辑不得擅自增加。

### 13.2 成本和资源控制

- 使用 EXPLAIN 获取预计行数和成本。
- 超过阈值拒绝执行。
- 数据库账号遵循最小权限。
- 使用只读事务。
- 设置 statement timeout。
- 外层包装 LIMIT，控制最大返回行数。
- 连接、权限和密码错误不进入模型修正。

### 13.3 失败交互

生成校验最多修正 3 轮，执行错误最多修正 2 轮。超限后保留已确认 QueryPlan，返回失败阶段、可理解原因和处理建议，不返回虚构结果，也不降低安全规则。

## 14. 患者级敏感数据安全设计

### 14.1 默认策略

当前已完成用户登录与基础角色认证，但尚未完成患者关系、用途授权和行列级数据权限，因此：

> 患者级明细、个人身份信息和病历内容默认拒绝；只开放经过授权的汇总分析。

不能仅依赖 Prompt，必须由程序强制执行。

### 14.2 Schema 安全元数据

建议为表和字段增加：

- `sensitivity_level`：L1 普通、L2 内部、L3 个人、L4 高敏医疗。
- `data_category`：身份、联系方式、诊断、病历、费用等。
- `patient_level`：是否属于患者粒度。
- `model_access`：允许、脱敏后允许、禁止出域。
- `export_policy`：允许、审批、禁止。

自动识别只能生成建议，最终由数据管理员认证。

### 14.3 四道强制门禁

```text
QueryPlan安全分类
→ Schema绑定敏感等级检查
→ SQL AST实际字段和粒度检查
→ 结果返回与模型出域检查
```

第一道：识别姓名、身份证、病历号、患者明细等意图。  
第二道：绑定后检查是否涉及 L3/L4 字段或患者明细表。  
第三道：检查 SELECT、WHERE、JOIN、GROUP BY、`SELECT *` 和结果粒度。  
第四道：检测返回列、身份证/手机号格式、小样本分组和模型出域内容。

任一道无法确定安全时均执行默认拒绝。

### 14.4 小样本推断保护

即使不返回姓名，小范围组合条件也可能锁定个人。生产环境应为汇总结果设置最小群体阈值，例如不足 5 人不展示，并禁止通过连续改变条件推断被隐藏数据。

### 14.5 模型数据出口网关

当前数据解读会将最多前 50 行结果发送给百炼，这在原型聚合场景可用，但不能作为医疗生产安全方案。上线前必须增加统一网关：

1. 检查字段敏感等级。
2. 删除、掩码或令牌化个人信息。
3. 仅允许聚合结果出域。
4. 限制字段、行数和文本长度。
5. 禁止病历自由文本出域。
6. 记录出域目的、字段、行数和模型。
7. 无法安全脱敏时使用本地规则摘要，不调用外部模型。

### 14.6 正式授权后的患者查询

未来即使完成认证，患者级查询也不应走自由模型 SQL，而应走认证接口或固定查询模板，并校验用户角色、患者关系、业务用途、审批、字段范围和有效期，全程审计。

## 15. 密钥、日志与审计

### 15.1 密钥管理

- 数据源密码加密保存。
- 生产必须配置独立 `SQLPILOT_SECRET_KEY`。
- API Key、数据库密码不得写入 Git、Prompt 和前端响应。
- 正式环境建议使用 KMS、Vault 或云密钥服务并支持轮换。

### 15.2 日志脱敏

日志允许记录请求 ID、用户、计划版本、执行状态、表、耗时、行数和错误类别。禁止记录明文密码、API Key、患者数据、完整模型载荷和敏感数据库错误。

### 15.3 审计事件

至少记录：登录、数据源配置、Schema 同步、语义定义变更、计划确认、SQL 执行、敏感请求拒绝、结果导出、模型出域、反馈审核和权限变更。

## 16. 结果呈现

结果层包含：

1. 中文列名、数据类型和单位。
2. 原始结果表格与截断提示。
3. 按维度和量纲生成的折线图、柱状图或多图看板。
4. 仅依据查询结果生成的摘要、关键发现和限制。
5. SQL、数据源、Schema证据、校验、成本和可信等级。

金额、人次和百分比等不同量纲不共用同一纵轴。模型解读失败时回退到本地摘要，不影响查询结果。

## 17. 记忆与学习闭环

记忆分为：

- 会话记忆：当前多轮需求。
- 用户偏好：展示和默认偏好，不覆盖正式业务口径。
- 业务记忆：需要来源、状态和有效期。
- 认证查询路径：审核通过的结构化 QueryPlan 和字段依赖。

用户点击“结果正确”只生成审核草稿。管理员核对结果和口径后才可以认证。复用的是结构化计划，不是历史裸 SQL；复用后仍需重新校验当前 Schema、安全规则和成本。

## 18. 状态与错误模型

主要会话状态：新建、澄清中、待确认、已确认、执行中、完成、失败。

错误应包括：

- 稳定错误码；
- 面向用户的中文消息；
- 是否可重试；
- 所在阶段；
- 去敏后的诊断详情；
- 建议操作；
- 请求 ID。

典型错误：模型不可用、模型输出协议错误、Schema 未同步、字段歧义、计划版本冲突、SQL 校验失败、成本超限、数据库权限失败、执行重试耗尽和敏感请求拒绝。

## 20. 后台任务设计

当前 Schema 同步使用 FastAPI BackgroundTasks，适合单机原型。生产环境应迁移到持久任务队列：

- API 仅创建任务并返回 job_id。
- Worker 执行目录扫描、Embedding 和知识版本激活。
- 支持重试、超时、心跳、取消和断点续作。
- 同一数据源使用分布式锁防止并发同步。
- 失败版本不激活，继续使用上一个有效版本。

## 23A. 高并发与性能设计

### 23A.1 当前实现与瓶颈

当前版本采用 FastAPI 异步接口，数据库访问和百炼调用也以异步方式组织，能够避免请求线程在网络等待期间被长期占用。但这只是并发基础，不代表已经完成生产级高并发设计。

当前主要瓶颈：

1. 系统元数据使用 SQLite，写并发和多实例能力有限。
2. 业务数据库部分链路按请求新建连接，缺少统一连接池治理。
3. QueryPlan、候选 SQL 和结果解读都可能调用外部模型，延迟和吞吐受百炼配额影响。
4. Schema 同步使用进程内 BackgroundTasks，服务重启后任务不能可靠恢复。
5. 查询结果和历史记录可能增大系统库、网络及浏览器渲染压力。
6. 同一用户重复提问可能重复进行 Embedding、规划和数据库执行。
7. 缺少全局并发上限、队列背压和分级降级策略。

因此当前版本适合作为单机演示和小规模验证，不能直接承诺生产高并发指标。

### 23A.2 性能目标必须先定义

性能优化前先按业务场景制定 SLO，而不是笼统要求“响应快”：

| 场景 | 建议关注指标 |
|---|---|
| 创建会话、读取历史 | P95 响应时间、吞吐量、错误率 |
| QueryPlan 生成 | 首次响应时间、P95模型耗时、超时率 |
| Schema RAG | P95检索时间、Top-k召回、缓存命中率 |
| SQL执行 | P95执行时间、扫描行数、超时和成本拦截率 |
| 结果解读 | P95模型耗时、降级率、Token消耗 |
| Schema同步 | 每分钟文档数、Embedding吞吐、失败恢复时间 |

正式指标需要根据部署资源、业务库规模和模型配额通过压测确定，设计文档不预设未经验证的 QPS 数字。

### 23A.3 服务无状态化和水平扩展

FastAPI 服务应保持无状态：会话、计划、任务和执行记录统一写入外部 PostgreSQL/Redis，不能依赖某个进程内存。前端请求通过负载均衡分发到任意实例，并使用 request_id、conversation_id、plan_version 和 query_id 定位状态。

生产建议：

- API 网关负责认证、限流、请求大小和超时。
- 多个 FastAPI 实例处理短请求。
- Schema同步、Embedding和长耗时任务由独立Worker执行。
- PostgreSQL保存系统状态，Redis承担短期缓存、分布式锁和队列协调。
- 不使用粘性会话维持正确性。

### 23A.4 数据库连接池

业务数据库和系统数据库分别配置连接池，避免每次请求重新握手，也避免应用实例耗尽数据库连接。

需要配置：

- `pool_size`：稳定连接数量。
- `max_overflow`：短时突发连接。
- `pool_timeout`：获取连接等待上限。
- `pool_recycle`：回收失效长连接。
- `pool_pre_ping`：借出前检查连接可用性。

总连接数必须满足：

```text
应用实例数 × 每实例最大连接数
≤ 数据库可分配给SQLPilot的安全连接预算
```

不能为了提高应用吞吐无限扩大连接池。业务数据库保护优先于单次请求成功。

### 23A.5 模型并发治理

模型通常是端到端链路中最慢、最昂贵且最不稳定的依赖，应单独设置：

1. 规划、SQL生成、结果解读分别使用独立并发信号量。
2. 按用户、租户和全局设置并发及速率限制。
3. 对429、连接超时等可恢复错误使用指数退避并加入随机抖动。
4. 使用短超时和有限重试，避免请求堆积。
5. 熔断器连续失败后暂停请求，快速返回可重试提示。
6. 模型额度不足时保留QueryPlan和任务状态，不重复消耗已完成步骤。
7. 结果解读属于非核心能力，可以降级为本地摘要；需求规划不能用不透明规则冒充模型成功。

请求优先级建议为：计划确认执行 > 交互式需求分析 > 结果解读 > 后台Embedding > 离线评测。

### 23A.6 缓存设计

可以缓存但必须带数据源和版本边界：

| 缓存对象 | 推荐键 | 失效条件 |
|---|---|---|
| Schema检索结果 | 数据源ID + Schema指纹 + 规范化问题 | Schema版本变化 |
| QueryPlan路径 | 数据源ID + Schema指纹 + 规范化累计需求 | 路径停用或Schema变化 |
| 认证语义定义 | 数据源ID + 语义层版本 | 定义发布、停用或回滚 |
| 查询结果 | 用户权限范围 + 计划哈希 + 数据版本 | TTL、数据刷新或权限变化 |
| Embedding | 模型版本 + 文本内容哈希 | 模型或文档变化 |

包含患者级或敏感数据的结果默认不缓存。缓存内容仍需加密、权限校验和审计，不能只凭缓存键返回。

### 23A.7 请求合并与幂等

同一会话、同一版本的重复确认或执行可能来自用户双击、网络重试或前端刷新。接口需要幂等键：

- 同一 `conversation_id + plan_version + plan_hash` 只能产生一个确认结果。
- 同一 `plan_hash + execution_idempotency_key` 不重复执行SQL。
- 同一数据源同时只允许一个Schema同步任务。
- 相同Embedding文档通过内容哈希去重。

正在执行的相同请求可以共享Future或任务ID，后续请求读取同一执行状态，防止缓存击穿和重复模型消费。

### 23A.8 背压、限流与排队

系统必须在容量耗尽前拒绝或排队，而不是让所有请求同时进入数据库和模型：

```text
API限流
→ 用户/租户配额
→ 服务并发信号量
→ 模型或数据库专用队列
→ 超时/取消
→ 降级或明确拒绝
```

队列需要最大长度和等待时间。超过阈值返回“系统繁忙，可稍后重试”，不能无限堆积导致内存耗尽。用户取消请求时，应尽量取消尚未开始的模型调用和数据库查询。

### 23A.9 数据库查询保护

并发查询首先保护业务数据库：

- 按数据源设置独立并发上限，避免一个库拖垮全局。
- 每条SQL设置statement timeout。
- EXPLAIN超过成本和预计行数阈值直接拒绝。
- 强制最大时间范围和返回行数。
- 大结果采用分页、游标或异步导出，不一次加载到内存。
- 报表型重查询进入离线任务队列，不占用交互查询资源。
- 对慢SQL记录计划、耗时和数据源，但日志不保存敏感结果。

### 23A.10 结果传输和前端性能

- 查询结果只返回当前页，图表只取必要数据点。
- 大表使用服务端分页和前端虚拟列表。
- 图表按量纲分组并限制可见点数。
- JSON响应启用压缩，但敏感响应应评估压缩侧信道风险。
- AI解读与原始结果解耦：表格先返回，解读失败不阻塞核心结果。
- 如果增加流式状态，只流转阶段和去敏事件，不实时输出模型内部思考内容。

### 23A.11 Schema同步性能

Schema同步拆成扫描、文档构建、Embedding、写入和激活阶段。优化方式：

- 根据Schema指纹只处理新增或变更对象。
- Embedding按服务限制批量提交并控制并发。
- 使用内容哈希复用未变化向量。
- 新版本全部写完后一次激活。
- 失败任务可断点续作，不删除上一有效知识版本。
- 离线同步与在线查询使用不同连接池和资源配额。

### 23A.12 超时、重试和熔断

各阶段使用独立超时预算：

```text
总请求预算
= 排队时间
+ Schema检索
+ 模型规划/SQL生成
+ SQL校验
+ 数据库执行
+ 结果加工
```

只有幂等且可恢复的错误才能重试。重试次数、间隔和总耗时都必须有上限。对持续异常的数据源或模型启用熔断，半开状态使用少量探测请求恢复，避免故障放大。

### 23A.13 性能监控

除平均耗时外，必须观察P50、P95、P99：

- 当前请求数、队列长度、拒绝数和取消数；
- API、模型、RAG、SQL各阶段耗时；
- 连接池使用率和等待时间；
- 模型429、超时、Token和熔断状态；
- 数据库慢查询、扫描行数、锁等待和超时；
- 缓存命中率、击穿和失效数量；
- 单实例CPU、内存、事件循环延迟和网络；
- 图表点数、响应大小和浏览器渲染时间。

### 23A.14 压测方案

压测必须使用脱敏或模拟数据，不使用真实患者数据。至少覆盖：

1. 只读历史查询基线。
2. Schema RAG高频检索。
3. 模型规划并发及429限流。
4. 确定性编译查询。
5. 模型SQL兜底和修正重试。
6. 慢SQL、成本超限和数据库故障。
7. Schema同步与在线查询同时运行。
8. 突发流量、长时间稳定流量和逐级压力测试。

验收不仅看吞吐，还要检查结果正确率、安全门禁是否失效、数据库是否被压垮以及服务恢复时间。

### 23A.15 建议实施顺序

P0：系统库迁移PostgreSQL、统一连接池、全局/数据源并发限制、超时、持久任务队列和基础压测。  
P1：Redis缓存、幂等执行、请求合并、模型熔断和结果分页。  
P2：增量Embedding、多级缓存、读写分离、自动扩缩容和容量预测。

## 24. MySQL 与 Oracle 扩展方案

不能只修改连接字符串，需要引入 `DatabaseAdapter`：

- 连接与健康检查；
- 表字段、注释、主外键目录读取；
- 标识符引用和参数绑定；
- 日期截断、字符串匹配、类型转换和分页；
- EXPLAIN/执行计划；
- 只读会话和超时；
- 错误分类。

确定性编译器应先生成方言无关IR，再由 PostgreSQL、MySQL、Oracle Renderer分别输出SQL；SQLGlot按数据源选择解析方言，并为每种数据库建立容器或独立测试环境。

## 25. AI Agent 研发知识地图

深入学习本项目时，建议按以下顺序：

1. **LLM基础**：Token、上下文窗口、temperature、结构化输出和幻觉。
2. **Prompt Engineering**：系统Prompt、Few-shot、约束、错误回灌和Prompt版本。
3. **结构化协议**：JSON Schema、Pydantic、校验、版本和兼容性。
4. **Agent状态管理**：状态机、多轮上下文、幂等、并发版本和失败恢复。
5. **RAG**：切分粒度、Embedding、向量库、混合检索、重排、召回评估和版本同步。
6. **Schema Linking**：表选择、字段映射、Value Linking、关系扩展和歧义确认。
7. **语义层**：指标口径、维度、码值、JOIN基数、认证和血缘。
8. **Text-to-SQL**：QueryPlan IR、确定性编译、模型生成、方言和多表规划。
9. **Guardrails**：AST白名单、业务一致性、安全策略、重试和熔断。
10. **工具调用**：明确工具输入输出、权限、超时、幂等和可观测性。
11. **记忆与学习**：短期记忆、长期记忆、用户偏好、审核和过期策略。
12. **评测**：单元测试、Golden Set、执行一致率、分层指标和失败归因。
13. **安全**：敏感分类、最小权限、脱敏、模型出域、审计和提示注入防护。
14. **工程化**：异步API、任务队列、缓存、限流、日志、监控、Docker和灰度发布。
15. **Human-in-the-loop**：需求确认、字段消歧、业务认证和高风险审批。

## 26. 推荐学习路径

### 第一阶段：先讲清主流程

使用同一个医保问题，说明输入、处理和输出，能够在3分钟内完成讲解。

### 第二阶段：理解三个核心对象

重点掌握 QueryPlan、SchemaKnowledgeDocument 和 SemanticDefinition，能够解释为什么需要它们。

### 第三阶段：读核心代码

依次阅读规划器、数据源同步、知识检索、会话服务、编译器、校验器和执行引擎。每个模块只回答：输入是什么、做了什么、输出是什么、失败怎么办。

### 第四阶段：走三个测试案例

1. 标准单表同比查询，走确定性编译。
2. 字段含义接近的查询，触发用户消歧。
3. 患者病历查询，触发敏感策略拒绝。

### 第五阶段：模拟面试

练习项目介绍、架构取舍、准确率口径、数据安全、模型兜底边界和未来多数据库改造。

## 27. 生产化待办优先级

P0：

1. 在现有身份认证和基础RBAC上补充数据范围、患者关系和用途授权。
2. Schema敏感标签与默认拒绝策略引擎。

4. 日志脱敏和完整审计。

4. 结果漂移监控和定期回归。

3. 模型路由、缓存和成本优化。

## 28. 面试总结话术

SQLPilot并不是让大模型直接连接数据库写SQL，而是把Agent拆成需求理解、结构检索、语义治理、计划确认、受控生成、安全执行和结果解释多个阶段。大模型负责自然语言理解和复杂查询泛化，QueryPlan作为中间协议，认证语义层控制正式业务口径，确定性编译器覆盖高频标准分析，模型只兜底复杂长尾。所有SQL都必须通过AST白名单、计划一致性、成本和只读事务检查。查询结果再生成中文表格、图表和文字解读，并通过人工审核的查询路径形成可控学习闭环。对于患者级敏感数据，生产设计采用默认拒绝、字段敏感标签、四道安全门禁和模型出域控制，而不是依赖提示词。
