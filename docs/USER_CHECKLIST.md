# 明日需要业务方处理的事项

## 必须确认

1. 核心指标口径
   - 医保基金支付总额
   - 统筹基金支出
   - 医疗总费用
   - 结算人次
   - 就诊人次/人数是否需要与结算人次区分
   - 每项指标的字段、聚合方式、单位、去重主键和排除条件

2. 时间口径
   - 默认使用结算时间、费用发生时间、入院时间还是出院时间
   - “今年”“本月”“同期”的业务截止日规则
   - 当月未结束时，同期是否比较到同一天

3. 医疗类别字典
   - 确认住院是否包含 `21、22、23、24、52、92`
   - 客户当地是否存在扩展码值
   - 字典版本、来源和生效日期

4. 默认数据范围
   - 有效结算标志的正式值
   - 退费、撤销、冲正记录的排除规则
   - 中途结算是否纳入

5. 权威对账样例
   - 至少提供5至10个已知答案的业务问题
   - 每个问题提供权威报表结果、筛选条件和统计日期

## 多表功能上线前必须提供

1. 各事实表主键或业务唯一键。
2. 表之间的认证连接字段。
3. 连接基数：一对一、一对多、多对一或多对多。
4. 一对多情况下各指标的去重或预聚合规则。
5. 机构、人员、就诊、结算、费用明细等实体的业务关系说明。

## 可以后补

1. 指标中文别名及常见口语表达。
2. 机构等级、病种、收费项目等扩展字典。
3. 指标预警阈值、异常解释模板。
4. 客户希望默认展示的图表和排序方式。
5. 对外报告所需的小数位、金额单位和脱敏规则。

## 在系统中的处理位置

- Schema字段中文名和别名：`/admin/schema`
- 认证指标、维度、码值与Join：`/admin/semantic-layer`
- 数据源同步和RAG检索测试：`/admin/data-sources`

建议先把四个核心指标、结算时间、医疗类别字典和默认排除规则设为认证定义，再开始扩展多表分析。
